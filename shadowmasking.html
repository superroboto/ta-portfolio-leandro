The Shadow-Driven Opacity Paradox

Making a character invisible in the shadows sounds like a relatively simple material effect. However, from a rendering pipeline perspective, this presents a fundamental logical paradox.

You cannot sample a shadow on a surface that doesn't know whether it should exist yet.

Why standard shading fails

In a standard deferred rendering pipeline, material properties (like opacity masking) are evaluated before lighting and shadows. This creates a circular dependency:

  • To know if the monster should be invisible, the shader needs to sample the shadow data at that exact pixel.
  • But if the monster is invisible, its geometry is culled and never rendered to the G-Buffer.
  • Because it isn't rendered, it cannot execute standard surface shading or sample light/shadow data at that location.

Render order

Geometry → LOCALIZED SHADOW DATA → Material/Opacity Mask → Lighting & Shadows.

The Solution

To bypass this limitation without killing performance, I decoupled the character’s visibility from the main shadow pass using a localized, lightweight depth-testing system.

For every light source hitting the character, the system generates a 64x64 depth render target from the light’s perspective. Because this RT is dynamically zoomed in and tightly focused only on the character’s bounding volume, a tiny 64x64 texture provides great texel density, resulting in sharp shadow masks at a cost that is virtually negligible.

Performance

Because depth is only captured from the perspective of light sources currently interacting with the character's bounding volume, runtime overhead remains exceptionally low.

  • Shadow Cost: ~0.024ms per active light source.
  • Scalability: Capped at 10 overlapping light sources simultaneously.
  • Resolution: Completely independent of screen resolution.

Tested on a mid-range Radeon RX 5700.
